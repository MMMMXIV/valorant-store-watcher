# スマホアプリ版 設計書（まとめて預かる・管理型）

> この文書は「将来的に iOS / Android のスマホアプリにする」ための設計案です。実装前の合意用で、まだ本番運用はしません。
> 想定人数: **約10人（増えたら拡張）** ／ サーバー: **未定（無料枠優先、将来は有料＋広告で収益化も想定）** ／ 同意画面: **あり**

### 決定事項（2026-11）
- **通知はスマホのプッシュ通知に一本化**。スマホ版に Discord 通知は入れない。**Discord 通知は Windows 版のみ**に残す。
- サーバーの置き場所・DB は **未定**。まずは無料枠で始め、人数が増えたら有料サーバーへ移行し、**アプリ内広告などで収益化**する案も視野に入れる。
- Tier表はスマホ版に入れない（Windows版のみ）。

> ⚠️ **収益化を入れると前提が変わる**（詳細は §11）。非公式APIを使い、他人の認証情報を預かるサービスを「有料・広告付き」で運営することは、無料の身内ツールより **法的・運営上の責任が大きく** なる。収益化は「増えたら」ではなく、始める前に別途判断する。

---

## 0. 最重要の前提（必ず読む）

このアプリは、各ユーザーの **Riotログイン情報（Cookie）をサーバーで預かって** 代わりにストアを確認します。これは次を意味します。

- 預かるCookieは **パスワードと同等**。サーバーが漏れれば **預けた全員のアカウントが乗っ取られうる**。
- **非公式方式**のため規約違反リスクがあり、運営者（＝あなた）に集中する。
- だから **本人同意を必須**にし、**暗号化・鍵分離・最小保持・退会削除** を設計に組み込む。

ゼロリスクにはできない。中央に鍵束を置く以上、漏れたときの影響範囲は大きいままである。この文書の対策は「漏れにくく・漏れても被害を抑え・本人が納得して使う」ためのもの。

## 1. 目的とスコープ

### 目玉機能
**ウィッシュリストに登録したスキンが自分のストアに並んだら、スマホにプッシュ通知する。**

### スマホ版に入れる
- ウィッシュリスト（検索・追加・削除・優先度）
- スキンカタログ（検索・絞り込み）
- Riotアカウント連携（複数アカウント）
- 本日のストア表示（アカウント別）
- バンドル／ナイトマーケットの表示・通知
- **プッシュ通知（目玉・これ一本）**
- 同意画面・退会（全データ削除）

> スマホ版の通知は **プッシュのみ**。Discord通知は Windows 版の機能として残す（スマホ版には設定項目を作らない）。

### スマホ版に入れない
- **Tier表メーカー**（PC版のみに残す）

## 2. 全体構成

スマホは「閉じている間に自分でチェックできない」ため、**サーバーが主役**になる。

```
                （毎朝 09:05 JST ＋ 失敗時リトライ）
  ┌────────────────────────────────────────────┐
  │  サーバー（常時稼働・クラウド無料枠）          │
  │                                              │
  │  巡回ワーカー ── 既存 core/ をそのまま利用     │
  │   1. 各ユーザーのCookieを復号                  │
  │   2. アカウントごとに順番にストア取得（間隔あり）│
  │   3. ID正規化 → ウィッシュリスト照合           │
  │   4. 一致 → プッシュ通知（＋任意でDiscord）     │
  │   5. バンドル/ナイトマーケット判定・通知        │
  │   6. 履歴・通知履歴を保存（重複通知防止）        │
  │                                              │
  │  API（アプリ用）                              │
  │   - ログイン受け取り（Cookie保存）             │
  │   - ウィッシュリスト編集                       │
  │   - 本日のストア取得                           │
  │   - 退会（全削除）                             │
  │                                              │
  │  DB（暗号化Cookie・ウィッシュリスト・履歴）     │
  └────────────────────────────────────────────┘
        ▲ HTTPS                        │ プッシュ
        │                              ▼
  ┌──────────────┐             Expo Push →（APNs / FCM）
  │ スマホアプリ   │ ◄───────────────────── 通知
  │ (iOS/Android) │
  │ Expo/RN       │
  └──────────────┘
```

## 3. 認証情報の扱い（ここが核心）

### 3.1 ログインの流れ
1. アプリ内の **WebView で Riot 公式ログインページ** を開く（`auth.riotgames.com`）。パスワードはサーバーに渡らない。2段階認証も本人が入力。
2. ログイン完了（`playvalorant.com/opt_in` へのリダイレクト）で **トークンとCookie（ssid等）** を取得。
3. アプリは Cookie を **サーバーに送信**（HTTPSのみ）。サーバーが暗号化して保存。
4. 以後、サーバーが Cookie で再認証してストアを取得する（今のPC版と同じロジック）。

> PC版と違い、Cookieが「本人のPC」ではなく「サーバー」に載る。ここがリスクの増える点。

### 3.2 暗号化と鍵の分離（必須）
- Cookie は **AES-256-GCM** などで暗号化して DB に保存する。
- **復号鍵は DB と別の場所** に置く：クラウドの「シークレット機能」や環境変数（例: Fly.io Secrets、VMのsystemd環境変数、クラウドKMS）。
  - こうすると **DBだけ漏れても復号できない**。
- 鍵はコードにも Git にも絶対に置かない。
- ユーザーごとに付加情報（ユーザーID）を認証タグに含め、取り違え・差し替えを防ぐ。

### 3.3 最小保持・分離・削除
- 保存するのは必要な情報だけ（Cookie、puuid、Riot ID、地域、ウィッシュリスト、履歴）。パスワードは保存しない。
- API は常に「ログイン中ユーザー本人の行」しか読み書きできない（他人のデータに触れない）。
- **退会ボタン**で、そのユーザーの Cookie・履歴・プッシュトークンを完全削除。

### 3.4 ログイン切れ
- 無人で2段階認証・CAPTCHAを突破しない。切れたら **本人にプッシュで「再ログインしてね」** を送り、アプリから再ログイン。
- 保存済みの再認証で延命できる間は自動更新（今の keepAlive と同じ）。

## 4. 同意画面（登録前に必ず表示）

アプリ初回ログイン前に、次を明示して同意を取る（同意しないと進めない）。

> **このアプリについて（必ずお読みください）**
> - これは Riot Games 公認ではない、非公式のファンアプリです。
> - ストアの確認には、Riotが発行する **ログイン情報（Cookie）をサーバーに預けます**。これはパスワードに近い情報です。
> - 万一サーバーから漏れた場合、あなたのアカウントが乗っ取られる危険があります。
> - 非公式の方法のため、Riotの規約に反し、アカウントに制限がかかる可能性がゼロではありません。
> - パスワードは預かりません。ログインはRiot公式ページで行います。
> - いつでも「退会」で、預けた情報をすべて削除できます。
>
> ☐ 上記を理解し、自分のアカウントで自己責任で利用します

同意の記録（日時・バージョン）もサーバーに残す。

## 5. 技術スタック（案）

| 領域 | 採用案 | 理由 |
|---|---|---|
| アプリ | **Expo (React Native)** | iOS/Android を1コードで。今のReact知識が活きる。Expo Push が簡単 |
| ログインWebView | `expo-web-browser` / WebView | Riot公式ページをアプリ内で開く |
| プッシュ | **Expo Push Notifications** | APNs/FCMを個別に扱わず無料で送れる |
| サーバー | **Node.js（既存 `core/` を流用）** | 照合・取得・通知ロジックをそのまま使える |
| DB | SQLite（永続ディスク）or Managed Postgres | 10人規模ならSQLiteで十分。無料枠に合わせる |
| 鍵管理 | プラットフォームのSecrets / 環境変数 | DBと分離 |
| スケジュール | node-cron 等（既存 Scheduler を流用） | 毎朝＋リトライ |

### 無料枠のサーバー候補（10人・常時稼働が必要）
毎朝「決まった時刻に動く」ため、**常時起動**が必要（スリープするタイプは不向き）。

1. **Oracle Cloud Always Free（VM）** — 本当に無料で常時起動のVMが持てる。自由度が高い。おすすめ候補。
2. **Fly.io** — 小さな常時起動アプリ＋Secrets管理が使いやすい。無料枠は変動するため要確認。
3. （非推奨）無料枠でスリープするもの（例: Renderの無料Web）→ 定時巡回に向かない。

> 注意：データセンターのIPからRiotにアクセスするため、家庭のIPより不自然に見える可能性がある（規約リスクの一部）。これは管理型である以上避けられない。

## 6. 巡回とスケジュール
- 既存の `Scheduler` / `StoreCheckService` をサーバーで再利用。
- 毎朝ストア更新後（JST 09:05目安、取得元の更新時刻があれば優先）に、**全ユーザー × 各アカウント** を順番に処理。
- Riotへの配慮：ユーザー間・アカウント間に間隔を空ける。失敗は指数バックオフでリトライ。
- 重複通知防止：既存の「通知履歴テーブル（account × period × skin × kind）」をそのまま使う。

## 7. データモデル（サーバー・追加分の概略）
```
users(id, riot_consented_at, consent_version, push_token, created_at)
riot_accounts(id, user_id, label, puuid, game_name, region, last_period_end)
riot_secrets(account_id, enc_cookie, nonce, tag)   -- 暗号化Cookie。鍵は別管理
wishlist(user_id, skin_id, priority, position)
store_snapshots / store_offers / notifications ...  -- 既存coreのスキーマを流用
```
- `riot_secrets` は他テーブルと分け、アクセス経路を絞る。
- 既存 `core` のストア/通知スキーマはほぼそのまま移植できる。

## 8. セキュリティ・チェックリスト
- [ ] Cookieは暗号化保存、鍵はDBと別管理（環境変数/Secrets/KMS）
- [ ] 通信は全てHTTPS、APIは本人のデータのみアクセス可（認可）
- [ ] ログインはRiot公式ページ、パスワードは受け取らない
- [ ] ログ・エラーに秘密情報を出さない（既存 `redact` を流用）
- [ ] 同意画面＋同意記録、いつでも退会で完全削除
- [ ] レート制限（Riotへ・APIへ）
- [ ] 依存の脆弱性チェック、サーバーOS更新
- [ ] バックアップに平文の秘密を含めない
- [ ] 2FA/CAPTCHA回避・ゲームメモリ読み取り・アンチチート回避は行わない

## 10. 段階的ロードマップ
1. **Phase A（土台・テスト用アカウント）**：`core` を使ったマルチユーザー・サーバー。暗号化保管・巡回・プッシュ送信を、**テスト用/擬似データ**で検証。
2. **Phase B（Expoアプリ雛形）**：ウィッシュリスト＋Riotログイン（WebView）＋プッシュ受信。**Androidで動作確認**（iOSはMacでExpoビルド）。
3. **Phase C（同意・退会・運用）**：同意画面、退会削除、鍵管理の本番化、無料枠へデプロイ。
4. **Phase D（配布）**：身内配布（Android: APK/内部テスト、iOS: TestFlight）。審査回避のため当面はストア公開しない。

> 本物の友達の認証情報を扱うのは Phase C 以降、**あなたのサーバー・あなたの責任**のもとで。この開発環境ではテスト用データのみ。

## 11. 制約・リスク（正直な整理）
- **iOSの実機ビルド・配布にはMacが必要**（この開発環境では作れない）。Androidは可能。
- ストア公開は **非公式API利用が審査で問題視される可能性** → 当面は身内配布（TestFlight / 直接APK）。
- 中央保管である以上、**漏えい時の影響は全員に及ぶ**。対策は被害軽減であり、ゼロにはできない。
- データセンターIPからのアクセスは、家庭IPより規約上目立つ可能性。
- Riotの仕様変更で、取得・ログインが予告なく止まることがある。

### 収益化（有料サーバー＋広告）を入れる場合の追加リスク
「増えたら有料・広告で収益化」は現実的な発想だが、**無料の身内ツールとは別物の責任**が発生する。始める前に必ず検討する。

- **Riotの規約**：非公式手段の利用に加え、**商用利用**はより強く問題視されやすい。収益化は Riot からの措置（アカウント／サービス停止、場合により法的対応）の引き金になりうる。
- **他人の認証情報で収益を得る**構図になる。漏えい時の責任が重くなり、「ただのファンツール」では済まなくなる。
- **個人情報・プライバシーの法的義務**：お金を取る・広告を出すと、プライバシーポリシー、データの取り扱い説明、問い合わせ窓口、未成年対応などの義務が現実的に発生する（日本の個人情報保護法、広告SDKのデータ送信など）。
- **アプリストアの規約**：広告SDKや課金は審査が厳しくなり、非公式API利用と合わせて公開が通りにくい。
- **税・会計**：収益が出れば申告の対象になりうる。

**おすすめの進め方**：
1. まずは **無料・身内限定・非商用** で作り、仕組みとリスク許容度を見極める。
2. 収益化は「人が増えたから自動で」ではなく、**その時点で改めて設計・法務面を見直してから**判断する（広告を足すのは後からでも技術的には容易）。
3. 収益化するなら、Riotの当時の規約・各国の法令・ストア規約を**その時点で確認**する（本設計書の責任範囲外）。
